Event Sourcing: Why Smart Developers Store State as Events

Quick Overview

Instead of storing the current state of your data, event sourcing stores every change that happened to that data as a sequence of events. Think of it like a bank statement - rather than just showing your current balance, it shows every deposit, withdrawal, and transfer that led to that balance. You can reconstruct the current state by "replaying" all the events from the beginning.

This approach fundamentally changes how you think about data persistence. Traditional systems overwrite the previous state when something changes. Event sourcing never loses information - it appends new events to an immutable log. When you need the current state, you fold (reduce) all events to compute it. This might sound inefficient, but it unlocks powerful capabilities like perfect audit trails, time travel debugging, and the ability to project your data into multiple read models optimized for different use cases.

Here's a simple example in Python:

from dataclasses import dataclass
from datetime import datetime
from typing import List
from enum import Enum


class EventType(Enum):

    USER_REGISTERED = "user_registered"

    USER_ACTIVATED = "user_activated"

    EMAIL_CHANGED = "email_changed"



@dataclass

class Event:

    aggregate_id: str

    event_type: EventType

    data: dict

    timestamp: datetime

    version: int



class UserAggregate:

    def __init__(self):

        self.id = None

        self.email = None

        self.is_active = False

        self.version = 0

    

    def apply_event(self, event: Event):

        if event.event_type == EventType.USER_REGISTERED:

            self.id = event.data['user_id']

            self.email = event.data['email']

        elif event.event_type == EventType.USER_ACTIVATED:

            self.is_active = True

        elif event.event_type == EventType.EMAIL_CHANGED:

            self.email = event.data['new_email']

        self.version = event.version

    

    def from_events(self, events: List[Event]):

        for event in sorted(events, key=lambda e: e.version):

            self.apply_event(event)

        return self

How to Implement It

Let's build a practical event sourcing implementation using Django and PostgreSQL. We'll create an order management system that tracks every change as events.

First, create the event store model:

# models.py
from django.db import models
from django.contrib.postgres.fields import JSONField
import uuid


class EventStore(models.Model):

    id = models.UUIDField(primary_key=True, default=uuid.uuid4)

    aggregate_id = models.CharField(max_length=255, db_index=True)

    aggregate_type = models.CharField(max_length=100)

    event_type = models.CharField(max_length=100)

    event_data = JSONField()

    version = models.IntegerField()

    created_at = models.DateTimeField(auto_now_add=True)

    

    class Meta:

        unique_together = ('aggregate_id', 'version')

        ordering = ['version']

        indexes = [

            models.Index(fields=['aggregate_id', 'version']),

        ]



class EventStoreRepository:

    def save_events(self, aggregate_id: str, aggregate_type: str, 

                   events: List[dict], expected_version: int):

        """Save events atomically with optimistic concurrency control"""

        with transaction.atomic():

            # Check current version

            current_version = EventStore.objects.filter(

                aggregate_id=aggregate_id

            ).aggregate(

                max_version=models.Max('version')

            )['max_version'] or 0

            

            if current_version != expected_version:

                raise ConcurrencyError(

                    f"Expected version {expected_version}, got {current_version}"

                )

            

            # Save new events

            event_objects = []

            for i, event in enumerate(events):

                event_objects.append(EventStore(

                    aggregate_id=aggregate_id,

                    aggregate_type=aggregate_type,

                    event_type=event['type'],

                    event_data=event['data'],

                    version=expected_version + i + 1

                ))

            

            EventStore.objects.bulk_create(event_objects)

            return expected_version + len(events)

    

    def get_events(self, aggregate_id: str) -> List[EventStore]:

        return EventStore.objects.filter(

            aggregate_id=aggregate_id

        ).order_by('version')

Now implement the order aggregate:

# aggregates.py
from decimal import Decimal
from enum import Enum
from typing import List, Optional


class OrderStatus(Enum):

    PENDING = "pending"

    CONFIRMED = "confirmed"

    SHIPPED = "shipped"

    DELIVERED = "delivered"

    CANCELLED = "cancelled"



class OrderAggregate:

    def __init__(self, order_id: str = None):

        self.id = order_id

        self.customer_id = None

        self.items = []

        self.status = None

        self.total_amount = Decimal('0')

        self.version = 0

        self._uncommitted_events = []

    

    def create_order(self, customer_id: str, items: List[dict]):

        """Business logic for creating an order"""

        if self.id is not None:

            raise ValueError("Order already exists")

        

        total = sum(Decimal(item['price']) * item['quantity'] for item in items)

        

        event = {

            'type': 'OrderCreated',

            'data': {

                'order_id': self.id,

                'customer_id': customer_id,

                'items': items,

                'total_amount': str(total)

            }

        }

        self._apply_event(event)

        self._uncommitted_events.append(event)

    

    def confirm_order(self):

        if self.status != OrderStatus.PENDING:

            raise ValueError("Can only confirm pending orders")

        

        event = {

            'type': 'OrderConfirmed',

            'data': {'confirmed_at': datetime.now().isoformat()}

        }

        self._apply_event(event)

        self._uncommitted_events.append(event)

    

    def ship_order(self, tracking_number: str):

        if self.status != OrderStatus.CONFIRMED:

            raise ValueError("Can only ship confirmed orders")

        

        event = {

            'type': 'OrderShipped',

            'data': {'tracking_number': tracking_number}

        }

        self._apply_event(event)

        self._uncommitted_events.append(event)

    

    def _apply_event(self, event: dict):

        """Apply event to change aggregate state"""

        if event['type'] == 'OrderCreated':

            data = event['data']

            self.id = data['order_id']

            self.customer_id = data['customer_id']

            self.items = data['items']

            self.total_amount = Decimal(data['total_amount'])

            self.status = OrderStatus.PENDING

        elif event['type'] == 'OrderConfirmed':

            self.status = OrderStatus.CONFIRMED

        elif event['type'] == 'OrderShipped':

            self.status = OrderStatus.SHIPPED

        

        self.version += 1

    

    def load_from_history(self, events: List[EventStore]):

        """Reconstruct aggregate from events"""

        for event in events:

            self._apply_event({

                'type': event.event_type,

                'data': event.event_data

            })

        self._uncommitted_events = []

        return self

    

    def get_uncommitted_events(self):

        return self._uncommitted_events.copy()

    

    def mark_events_as_committed(self):

        self._uncommitted_events = []



Service layer

class OrderService:
    def __init__(self, event_repository: EventStoreRepository):
        self.event_repository = event_repository
    
    def create_order(self, order_id: str, customer_id: str, items: List[dict]):
        order = OrderAggregate(order_id)
        order.create_order(customer_id, items)
        
        events = order.get_uncommitted_events()
        self.event_repository.save_events(
            order_id, 'Order', events, 0
        )
        order.mark_events_as_committed()
        return order
    
    def get_order(self, order_id: str) -> OrderAggregate:
        events = self.event_repository.get_events(order_id)
        if not events:
            raise OrderNotFound(f"Order {order_id} not found")
        
        order = OrderAggregate()
        return order.load_from_history(events)

Where to Use / Where NOT to Use

Good use cases:


  • Financial systems and audit-heavy applications: Banking, accounting, or any system where you need a complete audit trail and the ability to prove what happened when. Your PostgreSQL skills shine here with proper indexing strategies.

  • Collaborative systems with complex workflows: Document editing, project management, or any system where multiple users make changes and you need to track who did what. Perfect for building Discord bot automation that tracks server events.

  • Systems requiring temporal queries: "Show me what the system looked like last Tuesday" or "What would happen if we replay this process with different rules?" This is invaluable for debugging production issues and testing business rule changes.


Avoid when:

  • Simple CRUD applications: If you're just storing user profiles or basic product catalogs, the complexity isn't worth it. Traditional Django models work perfectly fine.

  • Performance-critical read-heavy systems: If you need sub-millisecond response times for reads and don't need the benefits of event sourcing, stick with optimized relational models or read replicas.


Common pitfalls to watch for:

  • Event schema evolution: Events are immutable, so plan for schema changes. Always version your events and write migration logic.

  • Event store performance: Without proper indexing on (aggregate_id, version), event replay becomes slow. In Oracle, consider partitioning large event tables.

  • Snapshot complexity: For aggregates with thousands of events, implement snapshotting carefully - bugs in snapshot logic can corrupt your entire aggregate state.


Key Takeaways

  • Event sourcing transforms how you think about data: You're storing the story of what happened, not just the current state - this mindset shift makes you a better system designer
  • Perfect for audit trails and compliance: Every change is recorded with full context, making it easier to build systems that meet regulatory requirements
  • Excellent debugging and testing capabilities: You can replay events to reproduce bugs and test different scenarios without affecting production data
  • Requires careful schema design: Events are immutable, so invest time in getting your event structure right from the start - use your PostgreSQL/Oracle skills for proper indexing and partitioning
  • Combines powerfully with CQRS and AWS services: Event sourcing pairs naturally with separate read/write models and cloud event streaming services like EventBridge and Kinesis
