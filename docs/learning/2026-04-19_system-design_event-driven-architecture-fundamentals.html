Event-Driven Architecture Fundamentals

Quick Overview

Event-driven architecture (EDA) structures systems around the production, detection, and consumption of events â€” discrete records of something that happened. Instead of ServiceA calling ServiceB.do_thing() directly, ServiceA emits ThingHappened and whoever cares subscribes. The producer doesn't know (or care) who's listening. The consumer doesn't know (or care) who produced the event.

That decoupling is the whole point. Request/response coupling forces you to know your collaborators: their addresses, their contracts, their availability. Event-driven coupling inverts the dependency â€” producers publish facts about the world, consumers react. Add a new consumer? The producer doesn't change. Remove one? Same story. This is why EDA shows up everywhere autonomous systems live: webhook pipelines, microservice choreography, LLM agent tool-calling loops, observability stacks.

The minimum viable event:

from dataclasses import dataclass
from datetime import datetime
import uuid


@dataclass(frozen=True)

class Event:

    event_id: str

    event_type: str

    occurred_at: datetime

    payload: dict



@classmethod

    def new(cls, event_type: str, payload: dict) -> "Event":

        return cls(

            event_id=str(uuid.uuid4()),

            event_type=event_type,

            occurred_at=datetime.utcnow(),

            payload=payload,

        )

Three things matter: a stable ID (for idempotency), a type (for routing), and a timestamp (for ordering/replay). Everything else is payload.

How This Makes You a Better Developer

If you're already building autonomous systems â€” Discord bots emitting work, executors picking it up, Jira syncing in the background â€” you're doing event-driven architecture whether you've named it or not. Naming it matters. Once you see the pattern explicitly, you stop writing brittle if webhook_source == "jira": ... branches and start writing handlers that subscribe to event types. Your Django signals, Celery tasks, Postgres LISTEN/NOTIFY, and Discord.py's @bot.event decorators are all the same shape: producer emits, dispatcher routes, handler reacts.

The career leverage is real. Every serious backend role past mid-level assumes you can reason about asynchronous boundaries: at-least-once vs exactly-once delivery, event ordering, replay, dead-letter queues, idempotency. You'll see this in AWS (SNS/SQS/EventBridge/Kinesis), in Postgres (logical replication, NOTIFY), in every message broker, and in every LLM agent loop (tool-call events, streaming tokens, intermediate messages). Getting fluent here is what lets you design a system where the news digest, memory compaction, Jira sync, and executor all run independently without stepping on each other â€” instead of one monolithic on_message that does everything and blocks the bot for 30 seconds.

How to Implement It

Start with an in-process event bus. Don't reach for Kafka on day one.

from collections import defaultdict
from typing import Callable, Awaitable
import asyncio
import logging


log = logging.getLogger(__name__)

Handler = Callable[[Event], Awaitable[None]]



class EventBus:

    def __init__(self):

        self._subscribers: dict[str, list[Handler]] = defaultdict(list)



def subscribe(self, event_type: str, handler: Handler) -> None:

        self._subscribers[event_type].append(handler)



async def publish(self, event: Event) -> None:

        handlers = self._subscribers.get(event.event_type, [])

        if not handlers:

            log.debug("no subscribers for %s", event.event_type)

            return

        results = await asyncio.gather(

            *(self._safe_invoke(h, event) for h in handlers),

            return_exceptions=True,

        )

        for r in results:

            if isinstance(r, Exception):

                log.exception("handler failed", exc_info=r)



async def _safe_invoke(self, handler: Handler, event: Event) -> None:

        try:

            await handler(event)

        except Exception:

            log.exception("handler %s raised on %s", handler.__name__, event.event_type)

            raise

Two things to notice. First, asyncio.gather(..., return_exceptions=True) â€” one misbehaving handler should never take down its siblings. Second, the bus logs but re-raises inside _safe_invoke so the gather still collects the exception. Silent failure is worse than noisy failure.

Now wire it up. Here's a realistic Discord bot slice where a message triggers three independent reactions:

bus = EventBus()


async def save_to_memory(event: Event) -> None:

    msg = event.payload["message"]

    await memory_system.append(msg)



async def maybe_trigger_news(event: Event) -> None:

    if "news" in event.payload["message"].content.lower():

        await bus.publish(Event.new("news.requested", {"channel_id": event.payload["message"].channel.id}))



async def log_engagement(event: Event) -> None:

    await engagement_tracker.record(event.payload["message"].author.id)



bus.subscribe("discord.message.received", save_to_memory)

bus.subscribe("discord.message.received", maybe_trigger_news)

bus.subscribe("discord.message.received", log_engagement)



@discord_bot.event

async def on_message(message):

    await bus.publish(Event.new("discord.message.received", {"message": message}))

The on_message handler is now one line. Adding a fourth behavior means writing a new subscriber, not editing on_message. Removing one means deleting a subscription â€” no other code changes.

Persistence and idempotency. For anything that crosses a process boundary, events need to survive restarts and handlers must be idempotent (safe to run twice). Postgres works fine as a durable queue via SELECT ... FOR UPDATE SKIP LOCKED:

CREATE TABLE events (
    event_id UUID PRIMARY KEY,
    event_type TEXT NOT NULL,
    payload JSONB NOT NULL,
    occurred_at TIMESTAMPTZ NOT NULL,
    processed_at TIMESTAMPTZ,
    attempts INT NOT NULL DEFAULT 0
);
CREATE INDEX ON events (event_type, processed_at) WHERE processed_at IS NULL;

async def claim_next_event(conn, event_type: str) -> Event | None:
    row = await conn.fetchrow("""
        UPDATE events SET attempts = attempts + 1
        WHERE event_id = (
            SELECT event_id FROM events
            WHERE event_type = $1 AND processed_at IS NULL
            ORDER BY occurred_at
            FOR UPDATE SKIP LOCKED
            LIMIT 1
        )
        RETURNING event_id, event_type, payload, occurred_at
    """, event_type)
    return Event(**row) if row else None

SKIP LOCKED lets multiple workers pull from the same table without blocking each other â€” you get a work queue for free, no Redis/RabbitMQ needed for small-to-medium load. Make handlers idempotent by keying side effects on event_id: "if I've already created a Jira ticket for event X, don't create another one."

When you outgrow Postgres, the graduation path is clear: AWS SQS for simple queues, SNS for fanout, EventBridge for routing rules, Kinesis for high-throughput ordered streams.

Where to Use / Where NOT to Use

Good use cases:


  • Fanout workflows â€” one input triggers many independent reactions (Discord message â†’ memory + engagement + news trigger)

  • Cross-service integration â€” Jira sync, webhook dispatch, notification pipelines where the producer shouldn't block on downstream latency

  • Agent/executor systems â€” LLM tool calls, streaming intermediate messages, long-running work that needs to report progress without tight coupling

  • Audit and observability â€” events are a natural audit log; replay them to reconstruct state or debug a production incident

  • Decoupling slow work from request paths â€” keep the Flask/Django response fast, emit an event, let a worker handle the expensive part


Avoid when:

  • You need a synchronous answer right now â€” a login check, a price quote, a "can this user see this resource?" authorization. Request/response is the right tool; events add latency and complicate the mental model.

  • You have one producer and one consumer that will never change â€” you've added indirection with no decoupling payoff. Just call the function.

  • Strong transactional consistency is required across the boundary â€” EDA is eventually consistent by nature. If the business rule is "the charge and the ledger entry must both succeed or both fail," that's a transaction, not two events.


Common pitfalls:

  • Assuming order. Most event systems give you at-least-once delivery with no ordering guarantee across partitions. Design handlers to tolerate out-of-order arrival, or use a stream with partition keys if ordering genuinely matters.

  • Forgetting idempotency. At-least-once means duplicate delivery is normal, not exceptional. If your handler isn't idempotent, duplicates will bite you in production, not in tests.

  • Event payloads that leak internals. Don't publish UserRowUpdated with the raw DB row â€” now every consumer is coupled to your schema. Publish UserEmailChanged with just what changed.

  • No dead-letter path. Handlers will fail. Without a DLQ or a failed_events table, you lose data silently or retry forever. Cap attempts; quarantine poison messages; alert on the quarantine queue.

  • Debugging-by-grep. When everything is decoupled, tracing a single user action across ten handlers is painful. Add correlation IDs to every event from the start â€” a trace_id that propagates through the chain turns "where did this request go?" from archaeology into one query.


Key Takeaways

  • Events are facts, not commands. OrderPlaced, not PlaceOrder. This framing shift is the whole mindset.
  • Start in-process, graduate to durable. An EventBus class is enough to learn the patterns. Reach for Postgres SKIP LOCKED before reaching for Kafka.
  • Idempotency is not optional. At-least-once delivery is the default everywhere â€” design handlers so running them twice is safe, key side effects on event_id.
  • Correlation IDs from day one. The debugging cost of distributed event flows compounds fast. A trace_id on every event pays for itself the first time you need it.
  • EDA is a decoupling tool, not a default. If there's no fanout, no async boundary, and no independent evolution â€” just call the function. Indirection without decoupling is pure cost.
