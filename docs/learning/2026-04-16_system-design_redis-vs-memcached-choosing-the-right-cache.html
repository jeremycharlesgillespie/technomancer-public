Redis vs Memcached: Choosing the Right Cache

Quick Overview

Both Redis and Memcached are in-memory key-value stores designed to sit between your application and your slower data sources (PostgreSQL, S3, third-party APIs, LLM inference). The point is the same: keep hot data in RAM so you don't pay the cost of recomputing or refetching it. But once you scratch the surface, they diverge sharply enough that picking the wrong one will cost you weeks of refactoring later.

Memcached is the minimalist. It's a distributed hash map: strings in, strings out, LRU eviction, multi-threaded, and brutally fast at exactly that one job. Redis is a data-structure server that happens to be excellent at caching. It speaks lists, sets, sorted sets, hashes, streams, pub/sub, geospatial indexes, and Lua scripting. It can persist to disk, replicate, cluster, and run server-side logic.

# Both look nearly identical for the basic case
import redis, pymemcache


r = redis.Redis(host="localhost", port=6379)

m = pymemcache.Client(("localhost", 11211))



r.setex("user:42", 300, "jeremy")     # 5-min TTL

m.set("user:42", "jeremy", expire=300) # 5-min TTL

The simple case hides the divergence. The moment you need a leaderboard, a rate limiter, or a queue, Memcached forces you back into your primary database while Redis handles it in one round trip.

How This Makes You a Better Developer

For someone running Django + PostgreSQL on AWS, picking a cache layer is a quietly load-bearing decision. The wrong choice shows up six months later as ElastiCache bills you can't justify, race conditions in your rate limiter, or a Discord bot that loses its conversation context every time the host restarts. Knowing when Memcached's simplicity is the feature versus when Redis's data structures save you from reinventing distributed primitives is the difference between a cache that disappears into the architecture and one that becomes a maintenance burden.

This knowledge also unlocks specific patterns for your stack: Django's cache framework abstracts both, but django-redis lets you use Redis as your session store, Celery broker, and cache simultaneously â€” collapsing three services into one. For your Ollama work, Redis is the obvious choice for caching expensive LLM completions with semantic keys, throttling per-user inference requests, and queueing jobs to your local GPU. For a Discord bot, Redis pub/sub gives you cross-process message passing essentially for free. Memcached can do exactly none of that â€” and that's fine, as long as you know when "exactly none of that" is what you want.

How to Implement It

Start with what you actually need. If your use case is "memoize the result of an expensive function for 60 seconds," both work. Reach for Memcached when you want the fewest moving parts.

Memcached with Django:

# settings.py
CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.memcached.PyMemcacheCache",
        "LOCATION": "127.0.0.1:11211",
    }
}


In a view

from django.core.cache import cache


def expensive_report(request):

    key = f"report:{request.user.id}"

    data = cache.get(key)

    if data is None:

        data = run_expensive_query()  # 2-second Postgres query

        cache.set(key, data, timeout=300)

    return JsonResponse(data)

That's the 80% case. Now consider what Memcached can't do well: anything stateful beyond "blob with TTL." Here's the same scenario in Redis where you also need a per-user rate limit:

import redis
from time import time


r = redis.Redis(decode_responses=True)



def rate_limit(user_id: int, max_per_minute: int = 60) -> bool:

    """Sliding-window rate limit using a sorted set."""

    key = f"rl:{user_id}"

    now = time()

    pipe = r.pipeline()

    pipe.zremrangebyscore(key, 0, now - 60)   # drop old entries

    pipe.zadd(key, {str(now): now})

    pipe.zcard(key)

    pipe.expire(key, 60)

    _, _, count, _ = pipe.execute()

    return count <= max_per_minute

Try writing that with Memcached. You'll end up doing read-modify-write cycles that race under load, or pushing it back to PostgreSQL where every check is a transaction.

A pattern I'd actually use for your Ollama setup â€” caching LLM completions with a content-addressed key:

import hashlib, json, redis


r = redis.Redis()



def cached_ollama(prompt: str, model: str, ttl: int = 86400) -> str:

    key = f"llm:{model}:{hashlib.sha256(prompt.encode()).hexdigest()}"

    if cached := r.get(key):

        return cached.decode()

    response = ollama_client.generate(model=model, prompt=prompt)

    r.setex(key, ttl, response)

    return response

For Discord bot conversation memory across restarts, use a Redis hash per user:

def remember(user_id: int, key: str, value: str):
    r.hset(f"ctx:{user_id}", key, value)
    r.expire(f"ctx:{user_id}", 60  60  24 * 7)  # 7-day rolling window


def recall(user_id: int) -> dict:

    return {k.decode(): v.decode() for k, v in r.hgetall(f"ctx:{user_id}").items()}

On AWS, both are available via ElastiCache. Redis Serverless now scales to zero between bursts â€” useful for hobby projects where idle cost matters. Memcached on ElastiCache is cheaper per GB of cache but gives you nothing beyond raw key/value, so you pay the savings back in application complexity.

Where to Use / Where NOT to Use

Good use cases for Redis:


  • Session stores, rate limiters, leaderboards â€” anywhere you need atomic operations on data structures.

  • Pub/sub or job queues â€” Celery with a Redis broker, or hand-rolled streams for ordered event processing.

  • LLM response caching, conversation memory, embedding caches â€” TTLs plus rich types fit your Ollama work directly.

  • When you need persistence â€” RDB snapshots and AOF mean you can survive a restart without a cold cache thundering herd against PostgreSQL.


Good use cases for Memcached:

  • Pure read-through caches in front of PostgreSQL with no need for atomicity beyond set/get.

  • Multi-threaded workloads where one cache node must saturate many cores â€” Memcached's threaded model genuinely beats Redis here.

  • Ephemeral, sharded caches where simplicity is a virtue â€” fewer features means fewer footguns and a smaller ops surface.


Avoid Redis when:

  • You need exactly one feature (cache with TTL) and want zero operational complexity. Don't run a Redis cluster to do what a single Memcached node handles.

  • You're tempted to use Redis as a primary database. It can persist, but treating it as your source of truth instead of PostgreSQL is a recipe for data loss surprises.


Avoid Memcached when:

  • You'll need anything beyond strings within six months. Migrations from Memcached to Redis are common; the reverse essentially never happens.

  • You need persistence across restarts, replication, or cross-process coordination.


Common pitfalls:

  • Cache stampedes â€” when a hot key expires, every request races to recompute. Use SETNX locks in Redis, or stale-while-revalidate patterns. Memcached has no good answer beyond add-based locking.

  • Treating Redis as durable storage â€” appendfsync everysec can still lose a second of writes on crash. PostgreSQL is your source of truth; Redis is a derived view.

  • Storing huge values â€” a 10 MB value blocks Redis's single-threaded event loop during serialization. Keep values small or chunk them.

  • Forgetting decode_responses=True in redis-py â€” half the bug reports in Python Redis projects are confusion between bytes and strings.

  • Unbounded memory growth â€” set maxmemory and an eviction policy (allkeys-lru is a sensible default). Otherwise the OOM killer eventually decides for you.


Key Takeaways

  • Memcached is a hash map; Redis is a toolkit. Pick the smaller tool when the smaller tool fits â€” but be honest about whether it actually fits.
  • The migration path is one-way. Memcached â†’ Redis is routine; the reverse is a rewrite. When in doubt, start with Redis.
  • Atomic data structures eliminate distributed-systems bugs. Sorted-set rate limiters and INCR counters replace fragile read-modify-write loops you'd otherwise build on PostgreSQL.
  • For your Django + Ollama + Discord stack, Redis collapses three services into one â€” cache, Celery broker, session store, pub/sub bus, LLM response cache. That consolidation is the real win.
  • Cache is a derived view, not a source of truth. Whichever you pick, design assuming the cache is empty on every cold boot and the system still works â€” just slower.
