OWASP Top 10: Common Vulnerabilities

Quick Overview

The OWASP Top 10 is a community-driven list of the most critical security risks to web applications, published by the Open Web Application Security Project. It's not a checklist you complete once â€” it's a taxonomy of how applications get broken, updated every few years based on real-world breach data and CWE (Common Weakness Enumeration) telemetry. The current categories are Broken Access Control, Cryptographic Failures, Injection, Insecure Design, Security Misconfiguration, Vulnerable Components, Authentication Failures, Software/Data Integrity Failures, Security Logging Failures, and Server-Side Request Forgery (SSRF).

It matters because most production breaches aren't zero-days â€” they're boring mistakes from this list. An intern's SQL injection in a Django view, a Flask app exposing /admin without auth, an AWS S3 bucket set to public, a pickle.loads() on untrusted input. Understanding the Top 10 lets you recognize these failure modes before they ship, and it gives you a shared vocabulary with security reviewers, pentesters, and compliance auditors.

Here's the archetype â€” a textbook injection bug that still shows up in code review:

# VULNERABLE â€” string concatenation into SQL
def get_user(conn, username):
    cursor = conn.cursor()
    cursor.execute(f"SELECT * FROM users WHERE username = '{username}'")
    return cursor.fetchone()


SAFE â€” parameterized query, driver handles escaping

def get_user(conn, username):
    cursor = conn.cursor()
    cursor.execute("SELECT * FROM users WHERE username = %s", (username,))
    return cursor.fetchone()

How This Makes You a Better Developer

For someone building autonomous systems on Python/Django/Postgres/AWS, the Top 10 is a lens that sharpens architectural decisions. A Discord bot that runs shell commands from user input is an Injection risk waiting to happen. An Ollama-backed agent that fetches URLs it gets from an LLM is SSRF-prone by construction. A Flask hub exposing a Jira-creation endpoint without auth is Broken Access Control. The same pattern â€” trust boundary crossed without validation â€” appears everywhere once you know to look.

Career-wise, this knowledge separates senior engineers from mid-level ones. Writing a feature is table stakes; writing a feature that survives adversarial input, rotated credentials, and a misconfigured IAM role is what gets you trusted with production. It's also the fastest path to credibility in code review: catching a timing-safe comparison miss or a missing SameSite=Lax cookie flag signals you think about systems the way security teams do. For autonomous agents specifically, you become the person who recognizes that the LLM is an untrusted input source â€” its outputs need the same validation as a form field.

How to Implement It

Start by mapping each Top 10 category to concrete controls in your stack. Here's a working reference for a Python/Django/Flask codebase.

A01: Broken Access Control â€” Enforce authorization on every endpoint, default-deny.

from functools import wraps
from flask import request, abort, g


def require_owner(f):

    @wraps(f)

    def wrapper(args, *kwargs):

        token = request.headers.get("X-API-Token")

        if not token or not constant_time_eq(token, settings.api_token):

            abort(401)

        g.is_owner = True

        return f(args, *kwargs)

    return wrapper



@app.route("/api/jira/create", methods=["POST"])

@require_owner

def create_jira_ticket():

    ...

In Django, prefer PermissionRequiredMixin or @permission_required over hand-rolled checks. For object-level access, use get_object_or_404(Model, pk=pk, owner=request.user) â€” the owner= filter turns "someone else's record" into a 404 automatically.

A02: Cryptographic Failures â€” Never roll your own. Use secrets for tokens, bcrypt/argon2 for passwords, and TLS for every network hop.

import secrets, hmac
from argon2 import PasswordHasher


ph = PasswordHasher()



def hash_password(pw: str) -> str:

    return ph.hash(pw)



def verify_password(pw: str, stored_hash: str) -> bool:

    try:

        return ph.verify(stored_hash, pw)

    except Exception:

        return False



def new_api_token() -> str:

    return secrets.token_urlsafe(32)



def constant_time_eq(a: str, b: str) -> bool:

    return hmac.compare_digest(a.encode(), b.encode())

A03: Injection â€” Parameterize queries, escape shell args, sanitize template input.

# SQL â€” always use the driver's placeholder
cursor.execute("SELECT * FROM ideas WHERE status = %s", (status,))


Shell â€” use subprocess with a list, never shell=True on user input

import subprocess
subprocess.run(["git", "checkout", branch_name], check=True)  # SAFE

subprocess.run(f"git checkout {branch_name}", shell=True)    # VULNERABLE



Django ORM â€” .raw() is fine if parameterized, .extra() rarely is

User.objects.raw("SELECT * FROM users WHERE id = %s", [user_id])

For autonomous agents: treat LLM output as untrusted. If your Ollama agent generates a shell command, run it through an allowlist, not an LLM-based "is this safe?" check.

A05: Security Misconfiguration â€” Ship with secure defaults. For Django, that means DEBUG=False, SECURE_HSTS_SECONDS set, SESSION_COOKIE_SECURE=True, CSRF_COOKIE_SECURE=True. For AWS, block public S3 access at the account level and use IAM least-privilege.

# settings.py â€” production
DEBUG = False
ALLOWED_HOSTS = ["api.example.com"]
SECURE_SSL_REDIRECT = True
SECURE_HSTS_SECONDS = 31536000
SECURE_HSTS_INCLUDE_SUBDOMAINS = True
SESSION_COOKIE_SECURE = True
SESSION_COOKIE_HTTPONLY = True
SESSION_COOKIE_SAMESITE = "Lax"
CSRF_COOKIE_SECURE = True
X_FRAME_OPTIONS = "DENY"

A08: Software/Data Integrity Failures â€” Never deserialize untrusted data with pickle, yaml.load (use safe_load), or marshal. Pin dependencies and verify signatures.

# VULNERABLE â€” pickle on untrusted bytes is RCE
cached = pickle.loads(redis_client.get(key))


SAFE â€” use JSON for cross-process serialization

cached = json.loads(redis_client.get(key))

A10: SSRF â€” Critical for any agent that fetches URLs. Validate that the resolved IP isn't internal before the request.

import socket, ipaddress
from urllib.parse import urlparse
import requests


BLOCKED_NETS = [

    ipaddress.ip_network("127.0.0.0/8"),

    ipaddress.ip_network("10.0.0.0/8"),

    ipaddress.ip_network("172.16.0.0/12"),

    ipaddress.ip_network("192.168.0.0/16"),

    ipaddress.ip_network("169.254.0.0/16"),  # AWS metadata!

    ipaddress.ip_network("::1/128"),

]



def safe_fetch(url: str, timeout: int = 5) -> requests.Response:

    parsed = urlparse(url)

    if parsed.scheme not in ("http", "https"):

        raise ValueError("scheme not allowed")

    ip = ipaddress.ip_address(socket.gethostbyname(parsed.hostname))

    if any(ip in net for net in BLOCKED_NETS):

        raise ValueError(f"blocked network: {ip}")

    return requests.get(url, timeout=timeout, allow_redirects=False)

The 169.254.169.254 AWS metadata endpoint is the SSRF crown jewel â€” one unchecked URL fetch and an attacker reads IAM credentials off your EC2 instance.

Where to Use / Where NOT to Use

Good use cases:


  • Any Flask/Django endpoint that accepts user input â€” especially ones exposed via Tailscale or the public internet

  • Autonomous agents that execute tool calls (shell, SQL, HTTP) based on LLM output â€” the LLM is an untrusted input source

  • Discord bot commands that interpolate user text into file paths, shell args, or API calls

  • CI/CD pipelines â€” run bandit, pip-audit, and trufflehog on every PR


Avoid when:

  • Treating the Top 10 as a compliance checklist â€” it's a heuristic, not a spec. "We handled A03" doesn't mean you're safe from injection; it means you handled the cases you thought of.

  • Security-theater controls that annoy users without reducing risk â€” a 24-character password requirement with 30-day rotation is worse than a passphrase + MFA.

  • Rolling custom crypto because "the library is too slow" â€” you will lose this fight.


Common pitfalls:

  • Trusting authenticated users too much. Auth is not authz. A logged-in user modifying /api/users/42/profile when they're user 17 is still Broken Access Control.

  • Logging secrets. A stack trace with the full request body in crash_log.md is a credential leak waiting to be grepped.

  • DEBUG=True in prod. Django's debug page renders settings and stack traces â€” one misrouted request and an attacker has your SECRET_KEY.

  • Using == on tokens. Timing attacks are real; use hmac.compare_digest.

  • Forgetting that LLM output is untrusted. Prompt injection means an attacker who controls any text the LLM reads (a fetched webpage, a Discord message, an RSS feed) can control its output. Validate downstream.


Key Takeaways

  • The Top 10 is a taxonomy of failure modes, not a checklist. Use it as a lens during design and review, not a box to tick before release.
  • Every trust boundary needs validation. User input, LLM output, third-party APIs, cached data â€” if it crossed a boundary, validate it on arrival.
  • Parameterize, don't concatenate. SQL, shell, HTML, URLs â€” if you're building a string with untrusted data, you're one edge case from a CVE.
  • SSRF is the sleeper hit for agent builders. Any tool that fetches URLs from LLM-chosen inputs needs IP allowlisting and redirect control, or it's one prompt injection away from reading 169.254.169.254.
  • Automate the boring checks. bandit, pip-audit, trufflehog, and django-check --deploy catch 80% of the Top 10 before human review â€” wire them into pre-commit and CI so they run without discipline.
