Semantic Versioning (SemVer) Best Practices

Quick Overview

Semantic Versioning â€” SemVer for short â€” is a versioning scheme that uses a three-part number format: MAJOR.MINOR.PATCH. Each segment communicates specific meaning. Bump the PATCH (e.g., 1.4.2 â†’ 1.4.3) for backward-compatible bug fixes. Bump the MINOR (e.g., 1.4.3 â†’ 1.5.0) when you add functionality that doesn't break existing behavior. Bump the MAJOR (e.g., 1.5.0 â†’ 2.0.0) when you introduce breaking changes. The version number isn't arbitrary â€” it's a contract with everyone who depends on your code.

Why does this matter? Because without a clear versioning strategy, upgrades become a gamble. If you maintain a Django library, an internal API package, or even a shared automation toolkit, your consumers need to know: "Can I upgrade safely, or will this break my deployment?" SemVer answers that question at a glance. It's the difference between a teammate confidently running pip install --upgrade your-package and them pinning to a specific version forever because they don't trust what "new version" means.

Here's what the version string looks like in practice:

Optional pre-release and build metadata tags extend this further: 2.0.0-beta.1+build.4817. The pre-release tag (-beta.1) signals instability, and the build metadata (+build.4817) is informational only â€” it doesn't affect version precedence.

How This Makes You a Better Developer

If you're working across Python packages, Django apps, PostgreSQL migration tooling, and AWS-deployed services, versioning isn't academic â€” it's operational. Consider a Django app that exposes a REST API consumed by multiple internal services. When you change a serializer field from optional to required, that's a MAJOR bump. When you add a new endpoint, that's MINOR. When you fix a query that was returning stale data from PostgreSQL, that's PATCH. Getting this right means your CI/CD pipelines on AWS can make intelligent decisions: auto-deploy patch and minor updates to staging, but gate major bumps behind manual approval.

This knowledge also directly impacts how you version your automation and RPA tooling. If you're building Python packages that wrap Ollama inference calls or Discord bot frameworks, SemVer lets downstream users â€” including your future self â€” trust the upgrade path. It's a skill that separates developers who "ship code" from developers who "ship reliable software." Recruiters and teams notice when your PyPI packages, GitHub releases, and internal libraries follow disciplined versioning. It signals maturity.

How to Implement It

Step 1: Define Your Version in One Place

For Python projects, use pyproject.toml as your single source of truth. Never scatter version strings across multiple files.

# pyproject.toml
[project]
name = "my-django-toolkit"
version = "1.3.0"
requires-python = ">=3.10"


[project.optional-dependencies]

dev = ["pytest", "ruff", "black"]

If you need to access the version at runtime (e.g., for a /health endpoint or Discord bot status), read it programmatically:

# my_toolkit/__init__.py
from importlib.metadata import version


__version__ = version("my-django-toolkit")

This way, pyproject.toml remains the single source of truth, and your code reads from it rather than defining a competing string.

Step 2: Automate Version Bumping

Don't manually edit version strings. Use a tool. bump2version (or its modern fork bump-my-version) integrates cleanly into Python workflows:

pip install bump-my-version

Configure it:

# pyproject.toml
[tool.bumpversion]
current_version = "1.3.0"
commit = true
tag = true


[[tool.bumpversion.files]]

filename = "pyproject.toml"

search = 'version = "{current_version}"'

replace = 'version = "{new_version}"'

Now bumping is a single command:

bump-my-version bump patch   # 1.3.0 â†’ 1.3.1
bump-my-version bump minor   # 1.3.0 â†’ 1.4.0
bump-my-version bump major   # 1.3.0 â†’ 2.0.0

Each command updates the version, creates a git commit, and tags it. This pairs well with a safe-update workflow where you branch, test, and merge.

Step 3: Use Pre-release Versions for Unstable Work

When you're building a new feature that isn't ready for production â€” say, swapping an Ollama model backend or adding a new Discord command handler â€” use pre-release tags:

bump-my-version bump minor --new-version 1.4.0-beta.1

This produces 1.4.0-beta.1, which pip treats as a pre-release. Users running pip install your-package won't get it unless they explicitly opt in with pip install --pre your-package. This is invaluable when deploying to a staging environment on AWS while keeping production stable.

Step 4: Map Database Migrations to Versions

This is where SemVer intersects with your PostgreSQL and Oracle work. Tie your Django migration history to version numbers using a changelog or migration naming convention:

# In your CHANGELOG.md or migration file
"""
Migration: 0042_add_audit_log_table.py
Introduced in: v1.4.0
Reversible: Yes


Adds the audit_log table for tracking API mutations.

"""



from django.db import migrations, models



class Migration(migrations.Migration):

    dependencies = [

        ("core", "0041_previous_migration"),

    ]



operations = [

        migrations.CreateModel(

            name="AuditLog",

            fields=[

                ("id", models.BigAutoField(primary_key=True)),

                ("action", models.CharField(max_length=50)),

                ("timestamp", models.DateTimeField(auto_now_add=True)),

                ("payload", models.JSONField(default=dict)),

            ],

        ),

    ]

This practice makes rollbacks sane. If v1.4.0 causes issues, you know exactly which migrations to reverse. For Oracle databases where DDL changes are more sensitive, this traceability is critical.

Step 5: Integrate with CI/CD on AWS

In your deployment pipeline, use the version tag to drive behavior:

# deploy_check.py â€” run in CI before deployment
import re
import subprocess


def get_current_version():

    result = subprocess.run(

        ["git", "describe", "--tags", "--abbrev=0"],

        capture_output=True, text=True

    )

    return result.stdout.strip()



def classify_bump(old: str, new: str) -> str:

    old_parts = [int(x) for x in re.findall(r"\d+", old)[:3]]

    new_parts = [int(x) for x in re.findall(r"\d+", new)[:3]]



if new_parts[0] > old_parts[0]:

        return "major"

    elif new_parts[1] > old_parts[1]:

        return "minor"

    return "patch"



if __name__ == "__main__":

    # Compare last deployed version vs current

    deployed = "1.3.0"  # read from SSM Parameter Store, etc.

    current = get_current_version()

    bump_type = classify_bump(deployed, current)



if bump_type == "major":

        print(f"MAJOR bump ({deployed} â†’ {current}): manual approval required")

        exit(1)  # block auto-deploy

    else:

        print(f"{bump_type} bump ({deployed} â†’ {current}): auto-deploy approved")

        exit(0)

Store your deployed version in AWS SSM Parameter Store or a DynamoDB table, and let your pipeline compare it against the git tag to decide whether to auto-deploy or pause for review.

Where to Use / Where NOT to Use

Good use cases:

  • Shared Python packages â€” any library installed via pip by other projects or teams. SemVer is the language pip, Poetry, and uv all understand for dependency resolution.
  • Internal APIs and Django services â€” when multiple services consume your API, the version number communicates backward compatibility. Pair it with API URL versioning (/api/v2/) for external-facing endpoints.
  • Automation and bot frameworks â€” if you're distributing a Discord bot toolkit or Ollama wrapper that others extend, SemVer tells plugin authors when they need to update their integration code.
Avoid when:
  • Application deployments with no external consumers â€” if you're deploying a monolithic Django app where no one imports your code as a library, SemVer adds ceremony without value. Use commit hashes, date-based tags (2026.04.11), or simple incrementing build numbers instead.
  • Rapidly iterating pre-1.0 projects â€” SemVer spec says anything under 0.x.y can break at any time. If you're prototyping and your API changes every day, don't waste energy agonizing over minor vs. major. Stay at 0.x and iterate. Adopt strict SemVer when you have real consumers.
Common pitfalls:
  • Forgetting that dependency changes are breaking changes. If your package drops support for Python 3.10 or upgrades a PostgreSQL driver with different connection semantics, that's a MAJOR bump â€” even if your code didn't change.
  • Treating MINOR as "small change." MINOR means new functionality, backward-compatible. A large new feature is still MINOR if it doesn't break existing behavior. Size of change and type of change are different axes.
  • Never reaching 1.0. Some projects stay at 0.x forever out of caution. If people depend on your code in production, you owe them the stability signal that 1.0+ provides. Ship it.
  • Bumping version without a changelog. A version number without context is just a number. Always pair bumps with release notes explaining what changed and why.

Key Takeaways

  • MAJOR.MINOR.PATCH is a contract, not a counter. Each segment has specific meaning â€” breaking change, new feature, bug fix. Respect the semantics.
  • Single source of truth. Define your version in pyproject.toml and read it everywhere else. Never duplicate version strings.
  • Automate the bump. Use bump-my-version to update the version, commit, and tag in one command. Manual edits invite mistakes.
  • Tie migrations to versions. When working with PostgreSQL or Oracle, link database schema changes to version numbers so rollbacks are traceable.
  • Let your CI/CD pipeline read the version. On AWS, use version classification to auto-deploy patches and gate major bumps behind approval â€” turning your version string into an operational decision point.
