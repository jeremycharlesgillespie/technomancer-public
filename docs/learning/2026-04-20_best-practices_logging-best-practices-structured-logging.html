Logging best practices: structured logging

best_practices • April 20, 2026

Quick Overview

Structured logging is the practice of emitting log messages as a series of key-value pairs rather than free-form text strings. Instead of writing a log line like "User 123 failed login due to: invalid password", you emit structured data like {"event": "login_failure", "user_id": 123, "reason": "invalid_password", "level": "error"}. This shift transforms logs from opaque narrative streams into machine-readable datasets. In the context of autonomous systems and AI tooling, where debugging non-deterministic LLM behaviors or race conditions in FPGA-driven pipelines is common, this distinction is not merely stylistic; it is fundamental to observability.

The "why" becomes clear when you consider the ecosystem you likely manage: a hybrid of Flask services running local Ollama instances, Django monoliths serving Discord bots, and backend databases like PostgreSQL storing session states. When an issue arises in a distributed or semi-distributed environment, unstructured logs require a human to scan gigabytes of text to find a pattern. Structured logs allow your Prometheus/Grafana stack to ingest and index data automatically, enabling automated alerting and rapid root-cause analysis without human pattern recognition. This reduces Mean Time To Resolution (MTTR) significantly, allowing you to focus on architecture and AI optimization rather than grep-ing through stdout.

Here is a simple comparison showing the shift from chaotic text to machine-actionable data:

Unstructured (Hard to parse, filter, or correlate):

logger.info(f"Processing request for {user_id} with model {model_name} on GPU {gpu_idx}")


Output: "Processing request for 12345 with model llama3:8b on GPU 0"

Structured (Instantly indexable, filterable, and enrichable):

logger.info(

    "Processing request",

    user_id=12345,

    model_name="llama3:8b",

    gpu_idx=0,

    response_time_ms=120

)


Output: {"event": "Processing request", "user_id": 12345, "model_name": "llama3:8b", "gpu_idx": 0, "response_time_ms": 120}

How This Makes You a Better Developer

Adopting structured logging elevates your skillset from "writing code that works" to "engineering resilient, observable systems." In the autonomous systems space, where your stack involves integrating local LLM inference (Ollama) with real-time Discord interactions, unstructured logs often lead to "heisenbugs" where issues only appear under specific load or hardware conditions. Structured logging provides the forensic clarity needed to debug these complex, stateful interactions. For a Senior Engineer, this knowledge opens doors to building self-healing infrastructure. By defining strict schemas for your logs, you enable downstream tools to automatically correlate a failed API call from your Flask service with the specific prompt context sent to Ollama and the latency spike on your specific NVIDIA GPU. This transforms you from a coder who patches symptoms into an architect who designs systems that expose their own weaknesses for automated remediation.

Specifically, this skill solves the "context loss" problem common in microservices and serverless architectures. When your Discord bot (Discord.py) hits a rate limit and retries via a background worker, unstructured logs might just say "Retry failed." Structured logs can tell you exactly which user channel, the specific Discord event ID, and the internal error code caused the failure, along with the cost implications for your AWS bill if the retry loop spins out of control. Furthermore, when optimizing for resource efficiency—a key interest of yours—structured logs containing tags like region, instance_type, or model_variant allow you to query your observability stack to identify which specific deployments are burning through credits unnecessarily, enabling precise cost optimization strategies.

How to Implement It

Implementing structured logging in Python is straightforward, but the choice of library dictates your long-term success. For your stack, python-json-logger (PJL) is often preferred for its zero-dependency footprint and strict JSON formatting, which integrates perfectly with standard AWS CloudWatch or ELK stacks. Alternatively, structlog offers a more feature-rich API ideal for complex tracing and tagging.

Below is a practical guide to implementing this across your specific environments.

1. The Foundation: Python & JSON

First, ensure your logging configuration is centralized. Do not use logging.basicConfig for production; instead, configure the formatter to output JSON. 
import json
import logging
from datetime import datetime


Use python-json-logger for strict JSON formatting

from python_json_logger import json_logger as json_logging


Configure the root logger

logging.basicConfig(
    format=json_logging.get_format(),
    datefmt=json_logging.get_date_format()
)


logger = logging.getLogger(__name__)



def track_llm_inference(prompt_tokens, response_tokens, latency_ms, model_name):

    """

    Track specific metrics for local Ollama inference.

    This allows filtering by model name or latency thresholds later.

    """

    try:

        logger.info(

            "inference_complete",

            extra={

                "prompt_tokens": prompt_tokens,

                "response_tokens": response_tokens,

                "latency_ms": latency_ms,

                "model_name": model_name,

                "status": "success"

            }

        )

    except Exception as e:

        logger.error(

            "inference_failed",

            extra={

                "error_type": type(e).__name__,

                "error_message": str(e),

                "model_name": model_name

            },

            exc_info=True

        )

2. Framework Specifics: Django & Flask

Django Integration:
Django's standard logger can be converted to structured format by overriding the logger class or using a third-party package like structlog-django. This ensures that when your Django views serve data to your Discord bot backend, every request carries a consistent trace_id and user_id.

# views.py example
import structlog
from django.http import JsonResponse


Bind context globally if using structlog

structlog.configure(
    processors=[
        structlog.stdlib.filter_by_level,
        structlog.stdlib.add_logger_name,
        structlog.stdlib.add_log_level,
        structlog.stdlib.PositionalArgumentsFormatter(),
        structlog.processors.TimeStamper(fmt="iso"),
        structlog.processors.StackInfoRenderer(),
        structlog.processors.format_exc_info,
        structlog.processors.JSONRenderer() 
    ],
    context_class=dict,
    logger_factory=structlog.stdlib.LoggerFactory(),
    wrapper_class=structlog.stdlib.BoundLogger,
    cache_logger_on_first_use=True,
)


logger = structlog.get_logger()



def discord_webhook_view(request):

    logger.info(

        "discord_webhook_dispatched",

        extra={

            "channel_id": request.POST.get("channel_id"),

            "message_type": "audio_stream", # Context specific to your use case

            "payload_size": len(request.body)

        }

    )

    # ... dispatch logic

    return JsonResponse({"status": "ok"})

Flask & Discord.py Integration:
When building your Discord bots, you often run Flask backends. Ensure the bot's internal logic (e.g., handling voice connections or sending audio to headsets) logs structured events. If the bot crashes, having bot_id, guild_id, and function in the log is invaluable.

# bot.py example
import logging
import discord
import json


Custom formatter for Discord.py handlers

class StructuredFormatter(logging.Formatter):
    def format(self, record):
        log_record = {
            'timestamp': datetime.utcnow().isoformat(),
            'level': record.levelname,
            'logger': record.name,
            'message': record.getMessage(),
        }
        
        # Add common context like environment or version
        log_record['environment'] = os.getenv('ENV')
        
        if record.exc_info:
            log_record['exception'] = format_exception()
            
        return json.dumps(log_record)


Configure logger specifically for the bot

handler = logging.StreamHandler()
handler.setFormatter(StructuredFormatter())
bot_logger = logging.getLogger('discord_bot')
bot_logger.addHandler(handler)
bot_logger.setLevel(logging.INFO)

3. Observability & Cost Optimization

Finally, leverage these logs in your Prometheus/Grafana stack. You can scrape logs (via Loki) and create queries like: sum(rate(structured_logs{model_name="llama3:8b", status="error"}[5m])) by (model_name) This directly answers: "How many times did my local LLM fail in the last 5 minutes?" allowing you to correlate this with CPU utilization or memory pressure on your FPGA/embedded host.

Where to Use / Where NOT to Use

Good use cases:


  • Autonomous Agent Loops: When an AI agent attempts to self-correct a code generation error, logging the attempt_count, error_reason, and corrected_code allows you to replay the execution in your local debug environment to verify the fix.

  • Discord Bot Event Tracing: For high-volume Discord bots handling audio streams or complex state machines, logging message_id, user_id, and command_type allows you to quickly identify if a specific user or channel is triggering memory leaks or rate limit throttling.

  • AWS Cost Attribution: Tag logs with cost_center or project_code. When your AWS bill spikes, you can query logs to see exactly which Flask service or Ollama deployment generated the excess compute load, rather than guessing.


Avoid when:

  • Interactive CLI Tools: Do not use complex structured JSON logging for local development CLI scripts intended for human reading in stderr. Humans prefer concise lines. Save structured output for ingestion into a backend (Loki/ELK/Splunk).

  • High-Throughput Micro-Kernels: If you are running an extremely lightweight embedded process (e.g., on an FPGA or Raspberry Pi for specific audio processing tasks), the overhead of Python's JSON encoder might be too high. In such cases, consider logfmt (structured text) or simply writing compact text logs that can be parsed by simple scripts, avoiding the latency of complex JSON serialization.


Common Pitfalls:

  • Variable Pollution: Avoid logging mutable variables directly. Instead, log copies or specific fields. If you log a large DataFrame or a massive dictionary representing an LLM response, you will crash the logger thread or bloat your disk I/O.

  • Hardcoded Messages: Never concatenate strings like f"Error: {error}". This destroys the structure. Always pass the error object or string as a named argument.

  • Ignoring Context: A log without context is useless. Always include trace_id or request_id in web service logs so that a 500 error in Flask can be correlated with the specific prompt sent to Ollama.


Key Takeaways

  • Logs are Code Artifacts: Treat logs as the primary source of truth for your system's state, not just error notifications. They are the "source code" of your runtime behavior.
  • Structured Enables Automation: Without structure, your Prometheus queries are blind. With structure, your observability stack becomes proactive, alerting on patterns like "LLM inference latency > 2000ms" instead of just "Service Down."
  • Context is King: The value of a log entry is proportional to its context. Always include identifiers (User ID, Model Name, Trace ID) so that a log entry tells a complete story of what happened and where.
  • Efficiency Matters: In a home server or cloud environment, logging strategy impacts cost and disk life. Choose the right granularity; log high-level events frequently, but reserve verbose debugging for specific DEBUG levels in controlled environments.
  • Future-Proof Your Debugging: By writing structured logs today, you ensure that when an issue surfaces in a month or a year (perhaps after upgrading Ollama or changing your FPGA firmware), you can instantly reconstruct the timeline of events without rewriting your grep commands.
