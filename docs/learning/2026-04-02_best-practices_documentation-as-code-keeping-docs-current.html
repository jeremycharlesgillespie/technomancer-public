Documentation as Code: Keeping Your Docs Current and Your Sanity Intact

Quick Overview

Documentation as code is the practice of treating your documentation with the same rigor, tools, and workflows as your application code. Instead of maintaining docs in separate wikis, Word documents, or knowledge bases that inevitably become outdated, you store documentation in version control alongside your codebase, write it in markup languages like Markdown, and automate its generation and deployment.

Think of it this way: when you update your Django models, your database migrations run automatically. When you push code to AWS, your CI/CD pipeline deploys it automatically. Documentation as code applies this same philosophy to your docs – they live with your code, version with your code, and deploy with your code. This isn't just about convenience; it's about creating a sustainable system where documentation stays current because updating it becomes part of your normal development workflow, not an afterthought.

Here's a simple example of what this looks like in practice:

# api/views.py
from django.http import JsonResponse
from rest_framework.decorators import api_view


@api_view(['GET'])

def user_stats(request):

    """

    Get user statistics endpoint.

    

    Returns aggregated user data from PostgreSQL.

    Used by the dashboard and reporting services.

    

    Example response:

    {

        "active_users": 1250,

        "new_signups": 45,

        "churn_rate": 0.03

    }

    """

    # Your implementation here

    return JsonResponse({"active_users": 1250, "new_signups": 45, "churn_rate": 0.03})

When this docstring changes, your API documentation automatically updates. When you refactor the endpoint, you're forced to update the docs in the same commit. That's documentation as code in action.

How This Makes You a Better Developer

As a Django developer working with PostgreSQL/Oracle and AWS, you're constantly juggling complex systems with multiple integration points. Documentation as code transforms you from someone who occasionally writes docs into someone who architects information systems. This shift in mindset makes you significantly more valuable to your organization and opens doors to senior and architect-level positions.

In your current stack, this approach solves real problems you face daily. When you're building Django REST APIs that integrate with multiple databases, having your API docs auto-generate from your serializers and views means stakeholders always see the current endpoint structure. When you're deploying to AWS with complex infrastructure, having your architecture diagrams and deployment procedures live in code means your documentation evolves with your infrastructure. You become the developer who not only builds reliable systems but ensures others can understand, maintain, and extend them – a crucial skill for tech leads and senior positions.

How to Implement It

Let's build a practical documentation-as-code system for a Django project. We'll use MkDocs with automated API documentation and integrate it into your development workflow.

Step 1: Set up the foundation

First, install the necessary tools:

pip install mkdocs mkdocs-material mkdocstrings[python] mkdocs-gen-files

Create a mkdocs.yml configuration file in your project root:

site_name: My Django API Documentation
site_description: API and system documentation


theme:

  name: material

  features:

    - navigation.tabs

    - navigation.sections

    - toc.integrate



plugins:

  - search

  - mkdocstrings:

      handlers:

        python:

          paths: [.]

          options:

            docstring_style: google

  - gen-files:

      scripts:

        - docs/generate_api_docs.py



nav:

  - Home: index.md

  - API Reference: api/

  - Database Schema: database.md

  - Deployment: deployment.md

Step 2: Create automated API documentation

Create docs/generate_api_docs.py to automatically generate API docs from your Django views:

"""Generate API documentation from Django views."""
import os
from pathlib import Path
import mkdocs_gen_files


def generate_api_docs():

    """Generate API documentation from Django app views."""

    

    # Define your Django apps

    django_apps = ['users', 'orders', 'analytics']

    

    for app_name in django_apps:

        app_path = Path(app_name)

        if not app_path.exists():

            continue

            

        # Generate documentation for views

        views_file = app_path / "views.py"

        if views_file.exists():

            doc_path = f"api/{app_name}/endpoints.md"

            

            with mkdocs_gen_files.open(doc_path, "w") as f:

                f.write(f"# {app_name.title()} API Endpoints\n\n")

                f.write(f"::: {app_name}.views\n")

                f.write("    options:\n")

                f.write("      members:\n")

                f.write("      - UserStatsView\n")

                f.write("      - OrderCreateView\n")

        

        # Generate model documentation

        models_file = app_path / "models.py"

        if models_file.exists():

            doc_path = f"api/{app_name}/models.md"

            

            with mkdocs_gen_files.open(doc_path, "w") as f:

                f.write(f"# {app_name.title()} Models\n\n")

                f.write(f"::: {app_name}.models\n")



if __name__ == "__main__":

    generate_api_docs()

Step 3: Document your Django views properly

Update your Django views with comprehensive docstrings that will auto-generate beautiful API docs:

# users/views.py
from rest_framework.viewsets import ModelViewSet
from rest_framework.decorators import action
from rest_framework.response import Response
from django.db import connections


class UserViewSet(ModelViewSet):

    """

    User management endpoints.

    

    Provides CRUD operations for user accounts with support for

    PostgreSQL and Oracle databases based on configuration.

    """

    

    @action(detail=False, methods=['get'])

    def analytics(self, request):

        """

        Get user analytics data.

        

        Queries both PostgreSQL (primary) and Oracle (legacy) databases

        to provide comprehensive user metrics.

        

        Args:

            request: HTTP request object

            

        Returns:

            Response: JSON containing user analytics

            

        Example:

GET /api/users/analytics/

Response:
{
"total_users": 15000,
"active_users": 12000,
"database_sources": {
"postgresql": 10000,
"oracle_legacy": 5000
}
}
            

        Database Queries:

            - PostgreSQL: Uses materialized views for performance

            - Oracle: Queries legacy user_stats table

        """

        # Connect to PostgreSQL

        pg_cursor = connections['default'].cursor()

        pg_cursor.execute("SELECT COUNT(*) FROM users_user WHERE is_active = true")

        active_users = pg_cursor.fetchone()[0]

        

        # Connect to Oracle for legacy data

        oracle_cursor = connections['oracle'].cursor()

        oracle_cursor.execute("SELECT COUNT(*) FROM legacy_users")

        legacy_users = oracle_cursor.fetchone()[0]

        

        return Response({

            "total_users": active_users + legacy_users,

            "active_users": active_users,

            "database_sources": {

                "postgresql": active_users,

                "oracle_legacy": legacy_users

            }

        })

Step 4: Integrate with your CI/CD pipeline

Add documentation building to your GitHub Actions workflow:

# .github/workflows/docs.yml
name: Build and Deploy Documentation


on:

  push:

    branches: [main, develop]

  pull_request:

    branches: [main]



jobs:

  docs:

    runs-on: ubuntu-latest

    steps:

      - uses: actions/checkout@v3

      - uses: actions/setup-python@v4

        with:

          python-version: '3.11'

      

      - name: Install dependencies

        run: |

          pip install -r requirements.txt

          pip install mkdocs mkdocs-material mkdocstrings[python]

      

      - name: Build documentation

        run: mkdocs build --strict

      

      - name: Deploy to S3 (production only)

        if: github.ref == 'refs/heads/main'

        run: |

          aws s3 sync site/ s3://your-docs-bucket/ --delete

        env:

          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}

          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}

Where to Use / Where NOT to Use

Good use cases:

  • API documentation for Django REST Framework projects: Auto-generate endpoint docs from your serializers and views. Every time you add a field or change a response format, the docs update automatically.
  • Database schema documentation for PostgreSQL/Oracle migrations: Keep your ER diagrams and table documentation in sync with your actual migrations. When you add a new model or field, the schema docs reflect the change immediately.
  • AWS infrastructure documentation: Store your architecture diagrams, deployment procedures, and configuration details alongside your Terraform or CloudFormation templates. When infrastructure changes, docs change with it.
Avoid when:
  • User-facing help documentation that non-technical stakeholders need to edit frequently: Marketing folks and product managers shouldn't need to know Git to update user guides.
  • Highly visual documentation requiring complex layouts: While Markdown is powerful, if you need complex visual layouts, dedicated documentation platforms might be better.
Common pitfalls to watch for:
  • Over-documenting implementation details: Focus on what other developers need to know, not every line of code. Your docstrings should explain the "why" and "what," not the "how" (that's what clean code is for).
  • Ignoring the generated docs: Just because it's automated doesn't mean you can ignore it. Review the generated documentation regularly to ensure it makes sense to readers.
  • Making it too complex: Start simple with basic Markdown files and docstrings. Don't try to build a complex documentation system on day one.

Key Takeaways

  • Documentation as code keeps your docs current by making them part of your development workflow, not an afterthought – when docs live with code, they get updated with code.
  • Use automated generation for API docs and schemas, but write architectural and process documentation manually – leverage the computer for what it does best (extracting information from code) and humans for what they do best (explaining complex concepts).
  • Integrate documentation building into your CI/CD pipeline – just like you wouldn't deploy code without tests, don't merge code without validating that documentation builds correctly.
  • Start with docstrings and gradually expand to full documentation systems – you can begin getting value immediately by improving your Python docstrings, then layer on automated generation and deployment later.
  • Documentation as code makes you more valuable as a developer – you become the person who not only builds systems but ensures they're maintainable and understandable by others, a crucial skill for career advancement.
